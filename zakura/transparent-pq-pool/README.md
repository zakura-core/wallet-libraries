# Transparent PQ address pool

`transparent-pq-pool` decides which PQ transparent keys a wallet may hand out, when it
needs more public keys from its signer, and how a restored wallet finds the keys it used.
It sits on top of [`transparent-pq-keys`](../transparent-pq-keys/README.md) and holds
public material only; the one secret-touching piece is the software key source, which
derives each key from the wallet seed and keeps only its public half. It is
unpublished. It does not build scripts or addresses, persist anything, or sign
transactions.

## Why a pool

An ECDSA wallet can derive any number of receiving addresses from an extended public
key. SLH-DSA has no such thing: every public key has to be generated by whoever holds
the seed. So the wallet keeps a batch of public keys the signer produced in advance and
hands out addresses from it. A software signer refills the batch immediately. A
hardware signer refills it as part of the next signing, or when the user asks for a
refresh, so receiving does not need a device connected.

## The window

One parameter, the window, is both the gap limit used to find keys on restore and the
number of keys kept ready ahead of the last used one. It is a required argument; the
design's example of 5 is not a default.

For each branch (receiving and change), let `highest_used` be the highest index known
to have received funds. Restore derives keys from index 0 upward and stops after
`window` consecutive unused keys, so it reaches exactly

```text
discovery_end = (highest_used + 1, or 0 if nothing was used) + window
```

The pool never provisions or issues an index at or beyond `discovery_end`. Every address
a wallet offers is therefore found again on restore. `discovery_end` only grows when a
payment arrives, not when an address is handed out: a wallet can have at most `window`
handed-out but unpaid addresses past the last used one.

## Handing out keys

`issue(branch)` returns the lowest provisioned key that has not been handed out, marked
fresh. When none is left, it returns the most recently handed-out key again, marked not
fresh, so the wallet can show it with a reuse warning. It never steps past the window to
hide that the pool is empty. If nothing has been provisioned yet, it fails and the
caller must replenish first.

The caller saves the pool's state (`state()`) before showing the returned address.
After a restart, `AccountPool::from_state` resumes from that state and does not hand the
same index out as fresh again. The caller also serializes concurrent requests; the pool
is an in-memory value.

Change uses the change branch through the same call. It never moves the receiving
index, and the receiving branch never moves the change index.

Paying an old address is always possible and costs no signatures. A payment to an old
address is spent with that address's key; rotation reduces reuse but cannot prevent it.

## Replenishing

`replenish_request(branch)` names the contiguous range of indices still missing below
`discovery_end`, or nothing when the branch is full. `replenish(branch, source)` asks a
`PublicKeySource` for that range and adds the result. `WalletSeed` is the software
source. A hardware source would answer the same request during signing; it is not part
of this crate.

`apply_batch` adds `(origin, public key)` pairs. It accepts:

- entries that continue the branch exactly at its next missing index, up to
  `discovery_end`. A source may return only part of the request; each entry is a
  complete key, and the rest of the request stays visible;
- entries the pool already holds with the same public key, which change nothing, so an
  interrupted replenishment can simply be retried.

It rejects the whole batch, changing nothing, if any entry belongs to another parameter
set, network or account, carries a public key for the wrong parameter set, leaves a gap,
lies at or beyond `discovery_end`, or disagrees with a key already held. The pool does
not authenticate the association between an origin and a public key; it trusts its
signer, as the keys crate's origin documentation says.

## Observing the chain

`record_received(origin)` records that a provisioned key has received funds. It raises
`highest_used`, which moves `discovery_end` and may create a new replenishment request.
A key used by another copy of the wallet also counts as handed out, so this device will
not offer it as fresh.

`set_confirmed_signatures(origin, total)` records how many of the key's signatures are
confirmed on chain, as recomputed from chain history (a total, so rescans do not double
count). A key that signed has received funds, so this also records it as used.
`highest_used` never moves down, including after a reorganization.

## Signature warning

Both parameter sets are designed for at most `2^64` signatures per key (FIPS 205 section
11). At 80% of that, `SIGNATURE_WARNING_THRESHOLD` (14,757,395,258,967,641,292), the pool
stops returning the key's address from `issue`, and `signing_permission` requires an
explicit force flag for every further signature.

This counts only confirmed on-chain signatures. It cannot see signatures made for
transactions that were never broadcast or never confirmed, or made by another device
whose transactions are not in the recovered history. A low count does not prove an
unused budget. No realistic wallet reaches the threshold; it is a backstop for hardware
signers that are never allowed to replenish.

## Restore

`discover` rebuilds an account's pool from a key source and a caller-supplied check of
whether a key has received funds. For each branch it replenishes up to `discovery_end`,
checks every new key, records the used ones, and repeats until `window` consecutive
keys past the last used one are unused. The restored pool has every index up to the
last used one marked handed out.

The check takes the public key so the caller can build the script and address, then
look them up on chain; this crate needs no script or address encoding. Confirmed
signature counts are supplied afterwards from chain history with
`set_confirmed_signatures`.

A hardware signer has to be connected during restore, because only it can produce the
public keys to check. Addresses that were handed out but never paid are below
`discovery_end` but cannot be told apart from never-issued ones, so a restored wallet
may offer them again as fresh.

## Not built here

Redeem scripts, P2SH addresses and the PQ script identifier; saving pool state to a
database, and any byte encoding of pool state or batches (backup and batch encodings are
still open); transaction signing, PCZT, and the hardware key source; multisig pools;
fees; network activation; and discovery beyond the window.
